## 사례 1. 외부에서 `/health` 접속 시 응답 없음 (timeout)

> ⚠️ **아직 실습 전입니다.** 아래 표는 [guide.md](guide.md) 10단계 재현 계획에 따른 **예상 기록**입니다. 실습 후 실제 시각, 명령 출력, 화면으로 바꾸고 이 줄을 지웁니다. 예상과 다르게 나온 부분은 다르게 나온 그대로 적습니다.

| 항목 | 내용 |
|---|---|
| 일시 | `2026-__-__ __:__` (KST) |
| 구분 | 실습 중 발생 / 재현하여 기록 (택 1) |
| **증상** | 내 PC에서 `curl -v http://<퍼블릭IP>/health` 실행 시 응답 없이 timeout. 브라우저도 로딩만 계속됨 |
| **가설** | ① 서버까지 패킷이 도달하지 않는다 (라우팅 / SG / 퍼블릭 IP 문제)<br>② 서버에는 도달했지만 Nginx가 받지 않는다 (프로세스 문제) |
| **검증** | 1. 증상이 timeout이지 connection refused가 아님 → 서버에 도달하지 못한 쪽(①)으로 좁힘<br>2. 서버 안에서 `curl -i http://localhost/health` → 200 OK. Nginx는 정상 → ② 제외<br>3. `sudo tail /var/log/nginx/access.log` → 외부 요청 기록이 **없음**. 패킷이 서버에 오지 않았다는 근거<br>4. Route Table 확인 → `0.0.0.0/0 → IGW` 있음, 서브넷 연결 있음<br>5. SG 인바운드 확인 → **80 규칙 없음** (22만 존재) → 원인 확정 |
| **조치** | SG `b3-1-sg-web` 인바운드에 `HTTP 80 ← 0.0.0.0/0` 규칙 하나만 추가 (다른 설정은 바꾸지 않음) |
| **결과** | 같은 PC에서 다시 `curl -i` → `HTTP/1.1 200 OK`, `OK`. `access.log`에 내 IP의 요청이 기록됨 |
| **재발 방지** | 배포 전 체크리스트에 "SG 인바운드: 80(전체), 22(내 IP)" 항목 추가. 접속 장애 시 "라우팅 → SG → 퍼블릭 IP → 서버" 순서로 점검 |

**근거 자료**
- 장애 화면: ![before](images/11-troubleshoot-before.png)
- 조치 후 화면: ![after](images/12-troubleshoot-after.png)

### 왜 이 순서로 확인했나

한 번에 여러 설정을 바꾸면 무엇이 원인이었는지 알 수 없다. 또 "포트를 전부 열기"처럼 보안을 희생하는 해결로 흐르기 쉽다.
그래서 **증상 → 가설 → 하나씩 검증 → 한 가지만 조치** 순서를 지켰다.

| `curl` 결과 | 의미 | 먼저 볼 곳 |
|---|---|---|
| timeout | 패킷이 서버에 도달하지 못함 | Route Table, SG, 퍼블릭 IP |
| connection refused | 서버엔 도달, 받을 프로그램 없음 | Nginx 실행 여부, 80 포트 대기 |
| 200 OK | 정상 | — |
