# 트러블슈팅 보고서

> 실습 중 **실제로 발생한 장애**를 기록했다. 서버 설정은 바꾸지 않고, 근거로 원인 범위를 좁혀 확정했다.

## 휴대폰 Chrome에서만 `/health` 접속 실패 (timeout)

| 항목 | 내용 |
|---|---|
| 일시 | 2026-10-20 10:36 ~ 10:57 (KST), 9단계 외부 검증 직후 |
| 구분 | 실습 중 발생 |
| **증상** | 휴대폰(Android) Chrome에서 `52.79.204.114/health` 접속 시 **`ERR_TIMED_OUT`** ("응답하는 데 시간이 너무 오래 걸립니다"). `http://`로 입력해도 실패. 같은 시간 Mac에서는 정상 |
| **가설** | ① 서버·SG·라우팅 등 **서버 쪽** 문제<br>② 휴대폰이 연결된 **네트워크**(와이파이)가 막음<br>③ **브라우저**(Chrome)가 `https://`(443)로 먼저 시도. SG는 443을 열지 않아 패킷을 버림 → 응답 없음 |
| **검증** | 1. 10:45 Mac에서 `curl -i --max-time 10 http://52.79.204.114/health` → **`HTTP/1.1 200 OK`, `OK`**. SG 80 규칙도 그대로 → **① 제외**<br>2. Chrome "항상 보안 연결 사용"을 **끔**(10:39) → 10:43 다시 접속해도 `ERR_TIMED_OUT`. 설정만으로는 해결 안 됨<br>3. 와이파이를 끄고 **LTE**로 접속 → Chrome은 여전히 실패 → **② 제외**<br>4. 같은 휴대폰, 같은 LTE에서 **삼성 인터넷** → **`OK`** (10:56) → 휴대폰·통신망은 정상, **Chrome에서만 실패** 확정<br>(검증 중 삼성 인터넷 첫 시도는 주소를 `52.79.204.144`로 잘못 입력해 실패. `.114`로 고쳐 다시 확인) |
| **원인** | **Chrome 클라이언트 문제**로 확정. 세부 동작은 **추정**: Chrome은 보안 연결 설정을 꺼도 내부적으로 `https://`를 먼저 시도하는 기능이 있고, SG가 443을 **거절하지 않고 조용히 버리므로** 빠르게 실패하지 못하고 timeout으로 끝난 것으로 보임 (Chrome 내부 동작이라 직접 확인하지는 못함) |
| **조치** | **서버는 바꾸지 않음.** 443을 열면 해결될 수도 있지만 HTTPS 인증서가 없고, "필요한 포트만 연다"는 SG 원칙에 어긋남. 접속 확인은 다른 브라우저(삼성 인터넷)로 함 |
| **결과** | 휴대폰(LTE, 집 네트워크가 아닌 외부망)에서도 `52.79.204.114/health` → **`OK`**. Mac(집 와이파이)과 **다른 네트워크에서도 접속됨**을 확인 |
| **재발 방지** | 접속 실패 시 **같은 요청을 다른 클라이언트로** 먼저 해 본다(`curl`, 다른 브라우저, 다른 네트워크). 하나라도 되면 서버는 정상이므로 서버 설정을 건드리지 않는다. 주소(IP) 오타부터 확인한다 |

**근거 자료**

![휴대폰 Chrome과 삼성 인터넷 비교](images/11-troubleshoot-mobile-chrome.png)

같은 시각 Mac 터미널 (10:45, 서버 정상 확인):

```text
aranglee@Arangui-MacBookPro ~ % curl -i --max-time 10 http://52.79.204.114/health
HTTP/1.1 200 OK
Server: nginx/1.24.0 (Ubuntu)
Date: Tue, 20 Oct 2026 01:45:31 GMT
Content-Type: text/plain
Content-Length: 3
Connection: keep-alive

OK
```

### 이 사례에서 배운 것

| 관찰 | 의미 |
|---|---|
| 같은 서버, 같은 주소인데 **클라이언트에 따라** 결과가 다름 | 실패했다고 바로 서버를 고치면 안 된다. 먼저 "어디까지 정상인가"를 다른 클라이언트로 가린다 |
| 실패 형태가 **refused가 아니라 timeout** | 응답 자체가 없었다는 뜻. SG는 허용하지 않은 포트(443)의 패킷을 거절 응답 없이 **버린다** |
| 문제를 풀려고 443을 **열지 않음** | 증상만 없애는 해결보다 최소 개방 원칙을 지키는 쪽을 택함 |

## 점검 기준 (이 실습에서 쓴 판단 근거)

한 번에 여러 설정을 바꾸면 무엇이 원인이었는지 알 수 없다. 또 "포트를 전부 열기"처럼 보안을 희생하는 해결로 흐르기 쉽다.
그래서 **증상 → 가설 → 하나씩 검증 → 조치** 순서를 지켰다.

| `curl` 결과 | 의미 | 먼저 볼 곳 |
|
이 실습에서 실제로 본 두 결과:

| 언제 | `curl`/브라우저 결과 | 뜻 |
|---|---|---|
| Nginx 설치 전, 내 PC → 80 | **Connection refused** (8 ms) | 요청은 서버까지 왔고, 80에서 듣는 프로그램이 없음 → [09a](images/09a-refused-before-nginx.png) |
| 휴대폰 Chrome (위 사례) | **ERR_TIMED_OUT** | 응답 자체가 없음. SG가 허용하지 않은 포트(443)의 패킷은 거절 없이 버려짐 |

## 사례 추가 방법

실습 중 다른 에러가 나면 위 표 형식(일시, 구분, 증상, 가설, 검증, 원인, 조치, 결과, 재발 방지)으로 추가한다.

> IAM 권한 오류라면: 에러 메시지에 나온 거부된 액션 이름(예: `ec2:CreateRoute`)을 근거로, **그 액션 하나만** [iam-policy.json](iam-policy.json)에 추가한다.
