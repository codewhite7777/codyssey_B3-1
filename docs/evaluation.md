## 항목 2. 내가 어떻게 했는가

### 외부 → IGW → Subnet → EC2 흐름 (다이어그램 번호 기준)
1. 사용자가 EC2의 퍼블릭 IP로 HTTP 요청을 보낸다.
2. 요청이 Internet Gateway에 도착하고, IGW가 퍼블릭 IP를 EC2의 프라이빗 IP로 바꿔 VPC 안으로 넘긴다.
3. Public Subnet에 도착한 요청은 Security Group을 만난다. 80 포트가 허용되어 있어 통과한다.
4. EC2의 Nginx가 요청을 받아 응답한다. SG는 stateful이라 응답은 자동 허용되고, Route Table의 `0.0.0.0/0 → IGW` 경로로 인터넷에 나간다.

### SG 규칙을 최소화한 기준
- 기준: "서비스와 관리에 꼭 필요한 포트만"
- 허용: **80** (서비스용이라 전체 공개), **22** (관리용이라 내 IP `/32`만)
- 미허용: **443** (HTTPS를 쓰지 않음), **3306/5432** (DB 없음), **전체 포트** (요구사항 위반, 공격 표면 확대)

### 외부 접속 검증으로 B를 고른 이유와 구성
- 이유: 고정 응답이라 성공/실패를 기계적으로 판단할 수 있고, 내 PC 터미널에서 응답 코드까지 증빙할 수 있다.
- 구성: Nginx에 `location = /health { return 200 "OK\n"; }` 추가 → `nginx -t` → reload, SG 80 허용, 서브넷 퍼블릭 IP 자동 할당.

### 리소스 추적·정리 기준
- 태그 `Project=b3-1`, 이름 규칙 `b3-1-*`
- 만들 때마다 체크리스트에 ID 기록 → 정리 시 그 목록대로 삭제
- 마지막에 EC2 Global View로 다른 리전 확인

## 항목 3. 왜 그렇게 했는가

### `0.0.0.0/0 → IGW` 경로가 필요한 이유
Route Table에는 기본으로 `10.0.0.0/16 → local`(VPC 내부)만 있다. VPC 밖으로 가는 패킷은 갈 곳이 없다.
외부 요청이 들어와도 **응답이 나갈 길이 없어서** 통신이 안 된다. 이 경로가 있어야 퍼블릭 서브넷이 된다.

### SG와 IAM의 차이, 최소 권한이 필요한 이유
- SG: 누가 **서버에 패킷을 보낼 수 있나** (네트워크)
- IAM: 누가 **AWS API로 리소스를 조작할 수 있나** (계정)
- 최소 권한이 필요한 이유: 키 유출이나 실수가 생겨도 피해가 권한 범위 안으로 제한된다.
- 적용: EC2 관련 액션만, 서울 리전만 허용. S3/RDS/관리자 권한 없음 ([iam-policy.json](iam-policy.json))

### SSH(22)나 DB 포트를 `0.0.0.0/0`으로 열면 안 되는 이유와 대안
- 이유: 인터넷에는 포트를 스캔하는 봇이 상시 돌고 있다. 열린 22나 DB 포트는 바로 무차별 대입 공격 대상이 된다.
- 대안
  - SSH: 내 IP `/32`만 허용 + 키 인증, 또는 Session Manager를 써서 22를 닫는다.
  - DB: Private Subnet에 두고, 앱 서버의 SG에서 오는 트래픽만 허용한다.

### 트러블슈팅에서 가설 → 검증 순서를 지킨 이유
- 여러 설정을 한 번에 바꾸면 무엇이 원인이었는지 알 수 없다.
- 근거 없이 고치면 "포트 전부 열기"처럼 보안을 희생하는 해결로 간다.
- 사용한 근거: `curl -v`의 timeout/refused 차이, `access.log` 기록 유무, SG 콘솔 화면 ([troubleshooting.md](troubleshooting.md))

## 항목 4. 상황이 바뀌면

### 외부 접속이 안 될 때 점검 순서
바깥에서 안쪽으로 좁혀간다.
1. **라우팅**: Route Table에 `0.0.0.0/0 → IGW`가 있고 서브넷에 연결되어 있나
2. **SG**: 인바운드 80이 열려 있나
3. **퍼블릭 IP/DNS**: IP가 있나, Stop/Start로 바뀌지 않았나, 브라우저가 `https://`로 바꾸지 않았나
4. **서버 프로세스/로그**: `systemctl status nginx` → `ss -tlnp | grep :80` → `curl localhost` → `access.log`/`error.log`

### IAM 권한이 부족할 때
- 관리자 권한을 주지 않는다.
- 에러 메시지에 나온 거부된 액션 이름(예: `ec2:CreateRoute`)을 확인한다. (실무에서는 CloudTrail 이벤트 기록의 AccessDenied도 근거가 되지만, 이번 실습 사용자에게는 과제 범위 밖이라 그 권한을 주지 않았다.)
- **그 액션 하나만** 정책에 추가하고 다시 시도한다. 필요하면 리소스나 리전 조건으로 범위를 더 좁힌다.

### 인스턴스를 2대로 늘려야 한다면
- 지금 구조의 병목: EC2 1대가 단일 장애점이고 AZ도 하나다. 사용자는 IP 하나로 접속하므로 트래픽을 나눌 방법이 없다.
- 추가할 것
  - 다른 AZ에 Public Subnet 하나 더 (ALB는 2개 이상 AZ 필요)
  - **ALB**: 요청을 두 EC2에 나눠 보내고, 헬스체크로 죽은 서버를 뺀다. `/health`를 그대로 쓸 수 있다.
  - EC2의 SG는 ALB의 SG에서 오는 80만 허용하도록 바꾼다.
  - 더 나아가면 Auto Scaling Group으로 대수를 자동 조절한다.

### Billing에 예상 못한 비용이 찍혔다면
1. Cost Explorer에서 **서비스별, 리전별**로 나눠 본다.
2. 의심 순서
   - 실행 중인 EC2 (프리 티어 외 타입, Unlimited 크레딧)
   - 퍼블릭 IPv4 / 인스턴스에 연결되지 않은 Elastic IP
   - 남은 EBS 볼륨, 스냅샷
   - NAT Gateway, ALB (시간당 과금)
   - 다른 리전에 실수로 만든 리소스 → EC2 Global View
3. 찾은 리소스를 정리하고, 다음부터는 태그와 체크리스트로 생성 시점부터 추적한다.
